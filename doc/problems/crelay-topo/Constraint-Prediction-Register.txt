Crelay-Topo Constraint Method -- Prediction Register
====================================================
Written 2026-09-19, BEFORE any extractor code exists.
This file is sealed on the date above.  Nothing in sections 3-6 may be
edited after the first extractor is written; scoring goes in section 7,
which is the only section that grows.

PURPOSE
-------
The constraint method's first run on crelay-topo is a VALIDATION run, not
a discovery run.  The problem is contaminated: twenty-two facts,
twenty-five lemmas and a sealed solution already exist for it.  Anything
the method "finds" here is something we already knew, and without a
prior commitment there is no way to tell derivation from recall.

So the run is scored, not celebrated.  This file registers, in advance,
what each extractor will emit and which existing register entries that
output should reproduce.  Afterwards the outcome is scored REGENERATED /
PARTIAL / MISSED / CONTRADICTED against these predictions.

Three outcomes, all useful:
  REGENERATED   the schema works; that entry need never be hand-derived
                again, on this problem or another.
  MISSED        populates Constraint-Schema-Gaps.txt with the question
                that should have been asked.
  CONTRADICTED  the jackpot.  One of the two derivations is wrong.  One
                is a multi-link argument chain built over five sessions;
                the other is a program reading the spec.  Suspect the
                chain first.

CONTAMINATION DISCLOSURE
------------------------
The assistant drafting this register has read Backward-Rules-Facts.txt in
full.  These are therefore NOT blind predictions and must not be
presented as such.  What is binding is section 3: the extractor
specifications are fixed now, in advance, so that no extractor can be
tuned toward a known answer while it is being written.  The honest
content of this exercise is:

  (a) whether the FIXED specifications in section 3 suffice to produce
      the outputs predicted in section 4, and
  (b) which register entries fall outside the schema entirely
      (section 6) -- this part is genuinely informative, because a
      structural blindness is a property of the method, not of what the
      author happens to remember.

1  METHOD POSITION
------------------
This register belongs to a third approach, alongside
Backward-Continuation-Prompt.txt and Forward-Continuation-Prompt.txt.
It is not a third search direction.  It is a second LEVEL:

  static profile (S1-S7)  ->  abstract layer (bodies x roles x segments)
  ->  abstract skeleton  ->  short forward searches realize each link
  ->  a surprising failure points at a missing constraint  ->  back to
  the code.

Constraints prove impossibility; search proves possibility.  Neither
does the other's job.  The method's payoff is not deduction of a plan
but a FORCED SKELETON plus short searches -- reducing what must be
searched, not eliminating it.

Grades, from the single-layer analysis:
  grade 1  definitional -- holds in every syntactically well-formed
           state.  From axioms defining derived predicates plus static
           instance facts.  No induction.
  grade 2  inductive invariant -- holds in every REACHABLE state.
           Earned by induction over the transition relation.
  grade 3  cost bound -- d(s,C) > k.  Relative to s.  LICENSES NO
           REFUTATION.  Confusing grade 3 for grade 2 is what produced
           T22 and the pre-test-12 alcove verdict.
  grade 4  trace/ordering -- constrains plans, not states.

3  EXTRACTOR SPECIFICATIONS  [SEALED 2026-09-19]
-------------------------------------------------

S1  CONTROL ALGEBRA                                          grade 1
    Input    every (controls <clause> <device> <polarity>) in the init
             database.
    Algorithm
      1 emit, per device, a Boolean function of primitives:
        normal   -> device == conjunction of clause literals
        inverted -> device == negation of that conjunction
      2 group devices by IDENTICAL clause (set equality).  Within a
        group: same polarity -> EQUIVALENCE pair; opposite polarity ->
        EXCLUSION pair (never simultaneously active, in any state).
      3 build the dependency DAG device -> primitives -> the devices
        those primitives depend on.  Report depth and any cycle.
    Output   control table; exclusion list; equivalence list; DAG with
             per-device depth.

S2  FUNCTIONAL-RELATION CENSUS                          grade 1 -> 2
    Input    define-types from the problem; the support-occupant and
             support type unions from tech/-support-occupancy.lisp; the
             arity/keying of dynamic relations.
    Algorithm
      1 a relation declared (rel KEY $value) is FUNCTIONAL in KEY.
        Report every such relation.  (on support-occupant $support) is
        the one that matters.
      2 intersect the support-occupant type union with the problem's
        declared extents -> the occupant pool.  Same for support.
      3 partition the occupant pool by recording side (plain vs starred
        RECORDING-COPY> partner).
      4 emit the cardinality bound: for any set P of supports,
        |{p in P : occupied}| <= |unheld occupants|, by injectivity of
        the witness map, which follows from (1).
      5 emit the bound separately per layer, since the recording view
        of a plate counts ghost occupants only.
    Output   functional relation list; occupant pool by layer; support
             pool; the cardinality bound with its per-layer readings.

S3  GATE-LABELLED REGION QUOTIENT                            grade 2
    Input    the propagated traversal relations (traverse-via,
             traverse-via>), each with its clause list.
    Algorithm
      1 build a directed graph over locations; label each arc with its
        clause list and its mode (walking/jumping/climbing).
      2 contract arcs whose clause list is EMPTY, treating an arc as
        bidirectional only when authored by traverse-via (not >).
        Record the contraction rule used; a clause naming a ladder or
        screen is NOT empty.
      3 emit the quotient, its arcs with clauses, and per-arc
        directedness.
      4 flag any gate appearing on no arc (a gate that blocks no
        movement -- an authoring signal, per the rumin lattice run).
    Output   region blocks; quotient arcs with clause and direction;
             movement-irrelevant gate list.

S4  CUT-KEEPER TABLE                                         grade 2
    Input    S1's control table, S3's quotient, has-position of every
             plate, has-location of every movable object at init, and
             the goal.
    Algorithm
      1 for each quotient arc, read its gate's controller from S1.
      2 locate the controller: which region block holds the plate's
        has-position, or which primitive (a switch) controls it and
        where that switch is reachable from.
      3 flag KEEPER-OBLIGATED when the controller is a plate lying in
        the region on the approach side of the arc: crossing requires a
        body left behind on that plate.
      4 for each object whose init region differs from a region it must
        reach, list the keeper-obligated arcs on its route.
      5 report any arc where the count of objects that must cross
        exceeds the bodies available to hold its keeper (join with S2).
    Output   per-arc: gate, controller, controller region, obligation
             kind; per-object: crossing list; the stranding conflicts.

S5  HEIGHT AND REACH LATTICE                                 grade 2
    Input    *vertical-type-constants*, has-height overrides, location
             levels from the third coordinate, *vertical-reach-limit*,
             and the placement/lift predicates in -support-elevation.
    Algorithm
      1 tabulate each type's height and each support's top.
      2 enumerate achievable TOPS for a carried object, by composing
        support-on-support where cleartop permits: ground, on each
        mobile support, on a held support.
      3 cross the achievable tops against the placement reach predicate
        to emit, for each (agent base, target support top) pair,
        whether a placement is legal.
      4 report every support top UNREACHABLE for placement from ground
        level.
    Output   height table; achievable-top enumeration; the placement
             legality matrix; the unreachable-from-ground list.

S6  BEAM SIGHTLINE TABLE                                     grade 2
    Input    apparatus-coords>, location-coords>, wall-segment>,
             gate-segment>, boundary-wall, has-height; the achievable
             tops from S5; and the beam-visible query itself.
    Algorithm
      1 beam-visible is a define-query with no state parameter and
        reads current state implicitly, so: copy *start-state*, force
        each subset of the gate open-bits directly into the idb, run no
        propagation.
      2 for each (station location, achievable near-elevation, beam
        endpoint object, far elevation) evaluate beam-visible.
      3 collapse over gate subsets to report, per (station, height,
        endpoint): visible always / visible only under gate set G /
        never.
      4 separately report LOS-VIA location occluders that block at the
        interpolated elevation -- a body standing there kills the hop.
    Output   the full visibility table; the gate dependency per entry;
             the location-occluder kill list.

S7  LANDMARK GRAPH AND ORDERINGS                             grade 4
    Input    S1's control algebra and the goal.
    Algorithm
      1 backward-chain from the goal conjuncts through S1: a device
        condition expands to its controlling primitives.
      2 a primitive that is a plate expands to "some occupant on it";
        a switch to "a toggle from a location that reaches it"
        (join S3, reach edges).
      3 emit the landmark set and the greedy-necessary orderings.
      4 state explicitly which relaxation is in force.
    Output   landmark graph; orderings; the relaxation used.

6  PREDICTED SCHEMA GAPS  [SEALED 2026-09-19]
----------------------------------------------
These are structural blindnesses, predicted in advance.  If any of them
turns out NOT to be a gap, the method is stronger than claimed and that
is itself a finding.

6.1  DELETE-RELAXATION IS BLIND TO KEEPER OBLIGATIONS.
     S7 extracts landmarks under a relaxation in which nothing is ever
     lost: a plate once depressed stays depressed, so no landmark
     charges the return trip, the second crossing, or the body left
     behind.  That is exactly the hole K11 through K17 were invented to
     fill, one at a time, over three sessions.  PREDICTION: S7 misses
     all seven, and S4 recovers only the existence of the obligation,
     never its cost.
     The question the schema should have asked: "for each landmark, what
     must remain true while later landmarks are achieved, and who holds
     it?"  This is the single most valuable gap to close, because it is
     domain-general.

6.2  NO EXTRACTOR CROSSES LAYERS.
     T23 requires counting ghost keeper obligations against
     recording-side gates -- S2's per-layer bound joined with S4's
     keeper table, restricted to the recording view, and then chased
     through the fork's switch seeding.  No extractor in section 3 does
     this join.  PREDICTION: T23 MISSED entirely.
     Given that T23 refuted thirty-two nodes at once, a layered variant
     of S4 is the obvious second-generation extractor.

6.3  CONSTRUCTIVE MECHANISMS ARE INVISIBLE, BY TYPE.
     T18, T20, F22, the T25 ferry.  Invariants are negative; they carve
     away.  No amount of static analysis produces a witness.  This gap
     is permanent and is the reason the method needs forward search as
     a component rather than a fallback.

6.4  SEARCH-TRANSFORMATION LEMMAS ARE OUT OF SCOPE.
     T4 T5 T6 T7 T8 T10 are arguments about deleting actions from a
     hypothetical plan.  They belong to the backward method's own
     apparatus.  Not a defect; recorded so the tally is read correctly.

6.5  THE CENSUS RE-DERIVATION IS THE RUN'S REAL PAYLOAD.
     S2 and S4 reach the occupant count by a path independent of
     T15 -> K13 -> T23 -> T24.  The backward analysis currently comes
     out ONE GHOST BODY SHORT of closing a plan and has deliberately
     not recorded that as a lemma.  Whatever S2/S4 report, the
     comparison is the most informative single number this run will
     produce.
     NOTE ON METHOD PURITY: this comparison cites no known solution.  A
     five-link derivation chain deserves independent re-derivation
     whether or not anyone knows the answer.  H6's analogue holds.

AMBIGUITIES, AND THE READING CHOSEN, BOTH RECORDED BEFORE THE RUN.
  A1  An EITHER alias whose components are all empty is installed by
      INSTALL-TYPES as the one-element list (NIL), not NIL, to keep it
      distinct from a leaf type declared with no instances.  Read as
      cardinality 0.  A naive LENGTH reads it as a singleton and would
      license every predicate over it.
  A2  "Quantifies over an empty type", for a relation, is read as: some
      argument position whose specification names at least one declared
      type and whose named types are all empty.  A position naming no
      declared type -- a fluent value domain such as $list, $mode,
      $rational, $fixnum -- is passed over rather than counted.  The
      unary relation implied by every type name, and the two indices a
      bijective declaration installs beside its canonical name, are

7.6  S1 SECOND SCORE -- G1's FIX.  Written 2026-09-19, BEFORE the run.
Under C2 this is a SECOND score for S1; 7.1 stands unrevised.

WHAT WAS WRONG.  S1 computed the CONTROL-ON aggregate and printed it as
the device's state.  The state is asserted by an update that combines
the aggregate with an override, and the two readings coincide only
where the override is dead.  S1 reached T3's conclusion without T3's
premise and would emit a FALSE grade-1 table, and false exclusion
pairs, on a jammer-bearing problem.

THE FIX.  A new block, device state axioms.  For every installed
update, find each IF whose test calls a query that reads CONTROLS and
whose consequent asserts a derived relation admitting a controlled
device.  Hold that call opaque, fold every other term by the extents
S0 computed, and reduce: :AGGREGATE means the override is dead and the
table is a claim about device state; anything else means it is not.
The pairs then carry an explicit qualification line, and any controlled
device no axiom covers is named.

THE SHAPE PROBLEM, WHICH IS THE POINT OF THE EDIT.  The override does
not have one syntactic form.  A gate ORs jamming in; a gears drive ANDs
not-jammed in.  CONTROL-ON's own docstring says so: "gate ORs it with
jamming, gears and gun AND it with not-jammed".  A reader that looked
for an OR disjunct would find no override on the blower and report it
clean -- the same silent mislabelling G1 filed, one level down.  The
reduction is therefore over the whole Boolean condition, not over a
disjunct list.
