G1  CONTROL AGGREGATE MISTAKEN FOR DEVICE STATE         [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, scoring S1 against F7 and T3.
Grade      would be grade 1, and wrongly so -- see below.

S1 prints one line per device of the form

    <device> == <DNF over its primitive controllers>

and derives its exclusion pairs from that form.  But the aggregate S1
computes is CONTROL-ON, not the device's state.  Gate.lisp's actual
axiom is

    open  <=>  jammed  OR  control-on

with an uncontrolled default supplied per device kind (NIL for a gate,
T for gears and guns).  S1 reads the CONTROLS fact and nothing else, so
it never sees the override disjunct.

On this problem the table is correct, but only because the jammer type
is unpopulated -- which is exactly what F7 states as a premise and what
T3 cites when it concludes that gate5 and gate7 are never both open.
S1 reaches T3's conclusion without T3's premise.  On a jammer-bearing
problem S1 would emit a FALSE grade-1 table and false exclusion pairs,
and a wrong grade-1 constraint refutes reachable nodes.  That is the
most expensive error the method can make; it is the shape of T22.

Note what did NOT go wrong: the hand analysis got this right, stating
the premise explicitly.  The program is the weaker derivation here.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    For each controlled device kind, what is the FULL axiom defining
    its state -- which disjuncts override the control aggregate, and
    which type extents must be empty for the aggregate alone to decide
    it?

FIX, domain-general
    S1 emits  state == aggregate  only after checking the override
    extents empty, and otherwise emits  state == override OR aggregate
    with the override named, and marks every pair conclusion
    conditional on the override.  The override is discoverable from the
    update that writes the device's state relation -- the same read set
    S1 already computes for its two-tier test -- so this costs no new
    input.  Closing G2 supplies the emptiness check.

STATUS
    CLOSED 2026-09-19 by S1's second score, section 7.7 of the
    register, scored REGENERATED.  S1 now emits a device state axiom
    block: for each update asserting a derived relation that admits a
    controlled device, under a test calling a CONTROLS-reading query,
    it holds that call opaque, folds the remaining terms by S0's
    extents, and reports whether the condition reduces to the aggregate
    alone.  Four axioms were found here and all four reduce, on the
    single premise that jammer is empty; the pair conclusions carry
    that premise explicitly and name what breaks without it.
    ONE THING THE FIX TAUGHT, worth carrying to the next problem: the
    override has no single syntactic form.  A gate ORs jamming in, a
    gears drive ANDs not-jammed in, and the recording-side pair names
    its override as a query call rather than a quantifier.  The fix
    proposed in this entry spoke of "the override disjunct", which
    would have matched the gate and passed the two AND forms through as
    clean -- this entry's own error, one level down.  A reduction over
    the whole Boolean condition is what the question actually requires.
    S1's crelay-topo output stands as scored in 7.1: the premise holds,
    so the numbers were right; what was defective was the derivation.


G2  NO EXTRACTOR OWNS TYPE EXTENTS                       [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, scoring S1 against F4 and F6.
Grade      grade 1.

Section 5 predicted F4 and F6 REGENERATED by "S1, plus type extents".
No extractor in section 3 emits type extents.  The prediction quietly
leaned on a component that was never specified, and C4 applies: those
entries score by what the extractors actually emit.

The facts at stake are emptiness and uniqueness facts about declared
types -- F6, "the problem has no threat objects, so SAFE holds
everywhere"; the uniqueness half of F4, "blower1 is the only blower".
An empty type is among the cheapest and strongest grade-1 constraints
there is: it collapses every predicate quantified over it to a
constant, with no induction and no search.  F6 and F7 are both
instances, and G1 above is a third.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    Which declared types are EMPTY in this problem, which are
    singletons, and which predicates does that make constant?

FIX, domain-general
    A type-extent census: every declared type with its cardinality,
    flagging empty and singleton types, and every relation whose
    signature quantifies over an empty type.  Cheap -- it reads *TYPES*
    and the relation signatures and nothing else.  Best placed as S1's
    step 0, since S1 needs it anyway for G1, rather than widening S2,
    whose pools are a different question.

STATUS
    CLOSED 2026-09-19 by S0, the type extent census, scored PARTIAL on
    its first run in section 7.5 of the register.  The census emits
    every type with its cardinality, the empty and singleton lists, the
    relations an empty type makes identically false, and the query and
    update sites an empty type makes constant.  Thirteen empty types
    and two constant predicates were emitted, so F6's mechanism and the
    uniqueness half of F4 are now computed rather than assumed.
    Closing it also supplied G1's emptiness check, as predicted: S0

G5  *TYPES* HOLDS SYNTHESIZED ALIASES, AND PROVENANCE IS UNREPORTED
                                                         [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, scoring S0's P1 and P3.
Grade      grade 1, and the entries are sound -- what is missing is
           their provenance.

S0 predicted 57 types and emitted 63.  The six extra are not authored
anywhere.  DISSECT-PRE-PARAMS (src/ww-support.lisp:630) interns every
INLINE (either ...) parameter specification as a type of its own, named
by sorting its components and joining them with +, and registers it in
*TYPES* and *TYPE-COMPONENTS* with the same (NIL) sentinel INSTALL-
TYPES uses for an all-empty alias.  Four of the six collapse to a
single object here and appear, correctly, as singletons.

Nothing S0 printed is wrong.  What is wrong is the label: the report
calls its table the declared types, and six of its rows are the
engine's own bookkeeping.  A later extractor that cites "every declared
type" -- S2's pools are the immediate case -- would inherit the
conflation, and a hand derivation from the source files will never
reproduce the count, which is precisely how a prediction gets scored
MISSED for the wrong reason.

Note what this says about the two derivations.  On S1 the hand analysis
was the stronger one.  Here the program is: it read the engine's table,
and the prediction read the sources and mistook them for the table.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    Which entries in a table the engine maintains were authored by the
    specification, and which did the engine synthesize while
    translating it -- and does the extractor's claim range over both?

FIX, domain-general
    Report provenance per type, from tables the engine already keeps:
    in *TYPE-SIGNATURES* means authored by DEFINE-TYPES; absent from it
    but present in *TYPE-COMPONENTS* means synthesized inline; absent
    from both means declared optional and never populated.  Three-way,
    costs no new input, and generalizes -- every extractor reading an
    engine table owes the same question.

STATUS
    CLOSED 2026-09-19 by S0's second score, section 7.9 of the
    register, scored REGENERATED.  Every row now carries its
    provenance: AUTHORED when *TYPE-SIGNATURES* holds it, since a real
    INSTALL-TYPES is that table's only writer; SYNTHESIZED when it has
    components but no signature; OPTIONAL when it has neither.  The
    split here is 46 / 11 / 6, and it is carried into the empty and
    singleton lists, which is where a later extractor reads them.  The
    relation header now counts relations and positions separately.
    THE GENERAL LESSON, which is why this entry is worth keeping after
    it closed: an engine table is not a transcript of the
    specification.  Every extractor reading one owes the same question
    -- which rows were authored, and which did the engine add while
    translating -- and the answer is usually available in another table
    the engine already keeps.


G6  A LAYER PARTITION OF BODIES IS NOT A LAYER PARTITION OF EFFECTS
                                                         [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, scoring S2's W6.
Grade      the numbers are grade 1; the LABEL on them claimed a grade-2
           reading of a different quantity.

S2 splits an occupancy pool by interaction layer and prints a bound per
layer -- "live view <= 4, ghost view <= 4" under a total of 8.  The
split is correct: four bodies carry a counterpart and four are
counterparts.  What is wrong is the assumption underneath the labels,
that a predicate reading the occupancy reads one layer's bodies.

The two consumers here do not agree with each other, and neither agrees
with the labels.  DEPRESSED is asserted from SUPPORT-OCCUPIED, whose
quantifier ranges over the whole occupant type with no layer test: a
plate is depressed by a ghost's weight as surely as by a live one, so
the live world's bound is EIGHT, not four.  RECORDING-DEPRESSED is
asserted from RECORDING-PLATE-OCCUPIED, which admits a ghost while the
cycle is open and a LIVE object after it closes.  So the recording
view's four is a real four, but WHICH four is selected by
RECORDER-CYCLE-CLOSED -- a state bit -- and is not a static property of
the partition at all.

The direction of the error is worth recording.  The hand prediction
(W6) was stronger than the program: it knew the physical consumer is
layer-blind.  The CODE was stronger than both: neither derivation had
the state-dependent switch.  That is the F19 rule paying for itself --
a data table read without the code that consumes it invites exactly
this.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    For each consumer of a functional relation, does it read the whole
    extension or a restricted part of it -- and is the restriction
    static, or selected at run time by a state bit?

FIX, domain-general
    An extractor that partitions a pool must report the partition
    ALONGSIDE ITS CONSUMERS, not alone.  For each derived relation
    asserted from a query over the placement relation, classify the
    query's restriction on the occupant: NONE (layer-blind), STATIC (a
    fixed class), or STATE-SELECTED (a class chosen by a dynamic
    condition), and name the condition in the third case.  The per-layer
    bound is then printed under the consumer it belongs to rather than
    under the pool, and a layer-blind consumer prints the whole-pool
    number where a reader will look for it.
    This is the same joining that section 6.2 of the prediction register
    predicted would be missing, arriving one extractor earlier than
    expected and in the cheaper half: 6.2 is about S2's bound joined
    with S4's keeper table, and G6 is about S2's bound joined with the
    consumers already in the substrate.  Closing G6 does not close 6.2,
    but an extractor that cannot say which layer its own bound is about
    cannot be joined with anything.

STATUS
    CLOSED 2026-09-19 by S2's second and fourth scores, sections 7.13
    and 7.17 of the register.  Every consumer of a placement relation is
    found, every site at which it reads that relation is listed with its
    restriction, and the bound is printed under the consumer rather than
    under the pool: DEPRESSED eight witnesses, layer-blind;
    RECORDING-DEPRESSED four, its class chosen at run time by
    (RECORDER-CYCLE-CLOSED).  The misreading this entry was opened for
    cannot be taken from the output any more.
    The wrong verdict that held it open through one score -- FIXED over
    a restriction whose switch sits inside a callee -- was G7's, and
    closed with it.
    TWO THINGS WORTH KEEPING AFTER THE CLOSE.  First, deduplicating the
    sites exposed a standing fact nobody had asked for: ON reaches the
    beam consumers through BASE alone, and BASE applies no layer test,
    so every elevation, reach and sightline computation in this
    substrate sees ghost bodies exactly as live ones.  Second, the
    consumer walk found that one update asserts a placement relation
    under a test reading ANOTHER placement relation, so these relations
    form a graph; an extractor that treats each in isolation will keep
    finding that out by surprise.


G7  THE SWITCH IS NOT BESIDE THE TEST -- IT IS INSIDE WHAT THE TEST CALLS
                                                         [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, scoring S2's second score against X4.
Grade      grade 1, and the verdict it produces is FALSE, which makes
           this the expensive kind.

G6's fix classifies a restriction as STATE-SELECTED when the Boolean
around the class test also holds terms that do not mention the key
variable -- those terms being the switch.  On the plate query that is
exactly right: the cycle marker sits beside the live and ghost tests
inside the disjuncts, and the classifier names it.

On the beam query it is exactly wrong.  The restricting terms all
mention the blocker, so the classifier finds no switch and reports the
restriction FIXED.  The switch is real and is one call deeper, inside
the body of the query the class test calls: that query classifies the
object through the copy relation and then reads the cycle marker
itself.  A reader of the output is told a class is fixed when it is
chosen at run time -- and a claim that something cannot vary, when it
can, is the shape of error the grades exist to prevent.

THIS IS THE THIRD RECURRENCE OF ONE SHAPE.  G1 filed the problem as
"the override disjunct" and the override had three syntactic forms.
G1's own proposed fix then committed the same error one level down,
matching the gate's OR and passing two AND forms through as clean.  Now
G6's fix looks for the switch at the syntactic level where it happened
to sit in the first example.  Every time, the correct move was the one
S0's CENSUS-FOLD already makes and 7.7's R8 already turned on: follow
the query calls.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    When an extractor looks for a term -- an override, a switch, a
    class test -- what makes it believe that term is at the syntactic
    level it is looking at, rather than inside a query the level it is
    looking at calls?

FIX, domain-general
    Make the switch search interprocedural, as the fold already is.
    When a restricting term is a query call, descend into that query's
    body and collect the terms there that do not mention the
    corresponding parameter, carrying the substitution.  Report the
    switch with the query it was found in, so a reader can see the
    distance between the test and the thing that moves it.
    THE STANDING RULE THIS SUGGESTS, and it is the reason to keep this
    entry after it closes: an extractor that walks a Boolean condition
    should treat a query call as an OPAQUE LEAF only when it has
    already asked what is inside it.  S1 holds the aggregate opaque
    DELIBERATELY and says so; every other opacity in this profile has
    been an oversight, three times running.

STATUS
    CLOSED 2026-09-19 by S2's third score, section 7.15, scored
    REGENERATED.  The switch search follows query calls, mapping each
    argument to the callee's parameter through the flat list the engine
    stores at :RAW-ARGS -- whose own comment says it is kept "for
    interprocedural symmetry walk", so the walk this needed had been
    anticipated by the engine and not by the extractor.  The site now
    reports STATE-SELECTED, naming both the switch and the query holding
    it one call from the test.
    TWO THINGS THE CLOSE TAUGHT.  The corrected verdict moved NO witness
    count, because the weakest-site rule had already decided each one
    through a layer-blind site -- a fix that had moved a count would
    have meant that rule was not doing what it claimed.  And the FIXED
    verdict was renamed: the walk descends four forms and the queries
    they call, so the output now says "no switch found", which is what
    it is entitled to say, rather than "fixed", which it is not.


G8  NO EXTRACTOR OWNS THE SEGMENT AXIS                   [OPEN]
------------------------------------------------------------------
Found      2026-09-19, building the region-free core of
           Constraint-Abstract-Model.txt.
Grade      the facts are grade 1 about the substrate; what is missing
           is that any extractor computes them.

The abstract model has three axes -- bodies, roles, segments -- and
sections 2 and 3 of the sealed spec supply the first two.  S2 gives the
occupant pool and S1 gives the roles.  NOTHING IN S1 THROUGH S7 EMITS
THE THIRD.

The segment structure here is set by the recorder: ghosts do not exist
until a fork creates them, and -recorder-cycle-boundary.lisp's
REMOVE-RECORDER-GHOST-STATE! deletes every dynamic proposition naming a
mapped ghost when a cycle ends.  So the body supply the whole model
counts against is a STEP FUNCTION of the segment -- four outside an open
cycle, eight inside one -- and that step is the difference between an
assignment being refutable and being merely unwitnessed.

S2 came close and stopped exactly short.  It reports the layer PARTITION
of the pool, 4 live and 4 ghost, and G6 taught it to print each bound
under the consumer that reads it.  But a partition of bodies says which
bodies are of which class; it does not say WHEN a class exists.  The
recording-side consumer's own class is already known to be chosen at run
time by (RECORDER-CYCLE-CLOSED) -- S2 prints that bit by name (7.15) --
and no extractor asks what that bit's lifecycle is.  The model therefore
reads two tech files by hand for its third axis, which is precisely the
hand-maintained-and-silently-stale failure M2 exists to prevent.

Note the direction of this one.  G1, G6 and G7 were all an extractor
reading a Boolean at the wrong syntactic level.  This is not that: every
extractor here is looking at the right level, and the axis simply has no
extractor pointed at it.  It is the same SHAPE as G2 -- a component the
model leans on that section 3 never specified -- one level up, at the
model rather than at an extractor.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    What SEGMENTS time in this problem -- which state bit opens and
    closes an epoch -- and across such a boundary, which objects, facts
    and capabilities are created or destroyed rather than merely
    changed?

FIX, domain-general
    An extractor that reports, for each dynamic relation, whether some
    update DELETES its propositions wholesale rather than transition by
    transition, and under which condition.  Wholesale deletion is what
    makes an epoch boundary, and it is visible statically: the update's
    body iterates a relation's extension and denies it, guarded by a
    test the extractor can name the same way S2 names a switch.  The
    output is the set of epoch-defining bits plus, per bit, the objects
    and relations that do not survive it.
    This is cheap -- it is the S2 consumer walk pointed at deletions
    instead of assertions -- and it is what the abstract model's third
    axis has to be read off rather than hand-derived.  It also answers a
    question A15 deferred from the other side: A15 excused the
    PRECONDITION side of consumption, and this excuses nothing, because
    a deletion is an assertion.

STATUS
    Open.  Blocks nothing immediately -- the hand reading in section 3
    of Constraint-Abstract-Model.txt is believed correct and is cited to
    its two files -- but every number in that section is unverified by
    any program, and is flagged as such there.


G9  A KEEPER CAN SERVE A SIGHTLINE, AND S4 ONLY READS MOVEMENT [OPEN]
------------------------------------------------------------------
Found      2026-09-19, scoring S3's N6 and section 4's
           movement-irrelevant line.
Grade      grade 1 about the geometry; the gap is that the extractor
           chain cannot reach it.

S3 reports gate4 as labelling no traversal arc, and the spec's own
coordinates say why: gate4 (28 10 28 13) is the only non-solid side of
the box x in [28,31], y in [10,13], closed otherwise by the boundary
wall and wall6.  No location lies in that box.  transmitter1 does.

So plate3 holds gate4 open, gate4 is what lets the beam out of the
chamber, and a body must stay on plate3 for as long as the beam is
wanted.  That is a keeper obligation in every sense the method cares
about -- continuous, costed in bodies, and on the critical path, since
gate8 is on the only route to the goal and gate8 follows the beam.

AND NO EXTRACTOR IN SECTION 3 CAN REACH IT.  S4's sealed input is
"S1's control table, S3's quotient, has-position ... and the goal", and
its algorithm is per-quotient-arc: read the arc's gate, locate its
controller, flag KEEPER-OBLIGATED when the controller lies on the
approach side.  gate4 IS ON NO ARC.  S4 as specified iterates a list
gate4 is absent from, so it cannot flag gate4 however carefully it is
written.  Section 4 predicts S4 will flag exactly five keeper-obligated
arcs INCLUDING "gate4 (plate3 @ L10)"; that prediction is already
unreachable by the extractor meant to produce it, and S3 showed this
before S4 was written.

The keeper obligations of this problem therefore live in TWO layers --
those that hold a door open for a BODY and those that hold one open for
a BEAM -- and section 3 has an extractor for the first only.  S6
computes sightlines and their gate dependencies, but S6 emits a
visibility table, not an obligation: it will say the beam needs gate4
open and never that someone must stand on plate3 to keep it there.
The obligation falls between them.

This is section 6.2's shape -- "no extractor crosses layers" -- on a
pair 6.2 did not name.  6.2 is about S2's per-layer bound joined with
S4's keeper table.  This is S4 joined with S6, and it is worse in one
respect: 6.2's join is missing, while this one is missing AND its
absence is invisible, because S4 will report five plate-controlled arcs
and look complete.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    A keeper holds a device open so that something may pass.  What are
    the KINDS of thing that pass -- a body, a beam, a stream, a line of
    sight -- and does the extractor that finds keepers iterate the
    passage structure of every kind, or only of the one whose graph it
    happens to have been handed?

FIX, domain-general
    Do not key the keeper search on the traversal quotient.  Key it on
    the CONTROLLED DEVICES, which S1 already enumerates, and ask of each
    what its state gates: a traversal clause (S3), a sightline (S6), a
    stream, a manipulation reach.  A device gating nothing is then a
    genuine authoring signal; a device gating something other than
    movement gets a keeper row in the layer it belongs to.  The
    obligation is the same shape in every layer -- a controller that
    must stay energized while the passage is used, and a body that must
    stay on it if the controller is a plate -- so one table serves all
    of them once the iteration runs over devices instead of over arcs.
    This also repairs the ordering: S4 currently has to wait for S3,
    and keyed on devices it waits for nothing.

STATUS
    Open, and it BLOCKS S4 AS SPECIFIED.  Section 3 is sealed, so S4 is
    not rewritten there; the choice is D's between writing S4 to the
    sealed spec and recording the gap in its score, or writing a
    device-keyed S4 as an amendment the way S0 was added.  Whichever is
    taken, the gate4 obligation must not be reported as five arcs plus
    silence.

G11  REGENERABLE IS NOT THE SAME AS RECOVERABLE              [CLOSED]
------------------------------------------------------------------
Found      2026-09-19, when 7.20's first attempted run hung.
Not a schema gap.  An apparatus defect, and the first one that
destroyed an artifact rather than degrading a score.

M2 is one of the method's load-bearing rules: regenerable output is
never hand-edited, because a hand-maintained table goes stale silently
and a wrong table looks like a right one.  Constraint-Static-Profile.txt
is therefore treated as disposable -- if it is wrong, fix the extractor
and rerun.

That reasoning has a hidden premise: THAT THE EXTRACTOR TERMINATES.
WRITE-STATIC-CONSTRAINT-PROFILE opened the target with :SUPERSEDE, which
truncates the existing file before the generator produces its first
byte.  When the classifier added in 7.20 hung, the profile was already
gone and the thing that would have regenerated it was the thing that had
just failed.  The old copy and the new copy were destroyed by the same
event.

What saved it was luck: a backup taken minutes earlier for the byte diff
N10 asks for, for entirely unrelated reasons.  Had that diff not been
queued, the session would have lost the artifact outright.

Note the shape.  The prompt's HOW IT LOADS section argues that a
loadable diagnostic is safe precisely because it cannot break a search:
"a diagnostic that cannot break a search is a diagnostic that can be
rewritten freely."  That is true and it is not the whole blast radius.
The diagnostic could not break a search and it destroyed a documentation
artifact, through a path the safety argument never considered, because
the argument was about what the code RUNS against and not about what it
WRITES.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    A generated artifact is safe to discard because it can be
    regenerated.  What destroys the old copy, when does it destroy it
    relative to the new copy existing, and does the thing that must
    succeed to regenerate it have any failure mode at all?

FIX, domain-general
    Generate into a temporary beside the target and rename over the
    target only after the generator returns.  The old copy then survives
    every failure mode of the generator -- an error, a hang, a machine
    losing power -- and the rename is the only moment of exposure.
    More generally: a destructive open is a commitment made before the
    work that justifies it, and every regenerate-in-place routine makes
    that commitment by default.

STATUS

    WRITE-STATIC-CONSTRAINT-PROFILE writes a sibling .tmp, deletes the
    target and renames, so a failed run now costs the run and not the
    artifact.  The destroyed file was restored from the backup and its

G14  AN INHERITED PREMISE IS NOT FILTERED BY THE VIEW ITS CONSUMER STATES [OPEN]
------------------------------------------------------------------
Found      2026-09-20, on RO's first staged run (register 7.27).
Grade      the printed premises are grade 1 and individually correct;
           what is missing is that the component indexes them by view.

RO takes a VIEW as an explicit input and allocates witnesses inside it.
Its witness pool is filtered correctly: the physical run drew only on
the physical pool, and the matching consumed nothing else.  But the
device-state premises RO inherits from S1 were printed unfiltered, so a
physical-view obligation carried both the physical and the recording
state axiom.  No printed claim was derived from the recording row, and
none is wrong.  The defect is that the OBLIGATION and the PREMISES
BESIDE IT are indexed by different things, and a reader has nothing in
the output telling them so.

This is the shape of G6 rather than of G8.  G8 asks which bit opens an
epoch and is about a missing extractor.  G6 established that a partition
of BODIES becomes a claim about EFFECTS only under a named consumer, and
fixed S2 by printing each bound under the predicate that reads it.  The
same move was never made for premises flowing the other way: when a
downstream component names a view, nothing checks that the upstream
facts it reprints are facts ABOUT that view.  S1 was right to emit every
device state it can prove; RO was wrong to reprint all of them under one.

The general hazard is not this problem's two layers.  Wherever a method
composes extractors, an upstream component states facts indexed by some
parameter -- a view, a layer, an epoch, a mode -- and a downstream
component fixes that parameter and inherits the facts wholesale.  The
inherited set is then silently wider than the claim it decorates, and
the widening is invisible precisely because every inherited fact is
true.

THE QUESTION THAT SHOULD HAVE BEEN ASKED
    When a component fixes a view, which of its inherited inputs are
    themselves indexed by that view, and what restricts them to it?  An
    input that cannot be shown to belong to the stated view is either
    filtered out or printed as OUT-OF-VIEW, never printed plain beside
    an in-view conclusion.

FIX, domain-general
    Give each inherited premise an index, computed rather than assumed:
    a state axiom is in-view when the relation it keys is read by a
    consumer restricted to that view, which is exactly the restriction
    S2 already computes per consumer site.  A premise whose index cannot
    be determined prints as UNINDEXED, which is weaker than in-view and
    stronger than dropping it.  The rule generalizes past layers to any
    parameter an upstream component ranges over.
    This is a reporting and provenance fix, not a change to any
    allocation: RO's matching already reads the view-filtered pool.

STATUS
    Open.  No result depends on it.  RO's first score (7.27) stands as
    taken, and its run output is retained unedited.  Implementing the
    fix requires its own approval, its own commitments appended to
    register section 7, and a fresh score; it must not be folded into
    7.27 or used to revise it.

    UPDATE 2026-09-20, later the same day.  Still OPEN, now SPECIFIED
    AND APPROVED but NOT YET IMPLEMENTED.  The design is
    Constraint-Role-Obligations.txt section 7; the commitments, written
    before any of the fix's code exists, are register 7.28.  The index
    is computed by walking UPWARD from a state relation to the consumers
    that read it and resolving each read site's governing layer-class
    test to a class by the position the tracked variable occupies in the
    layer-pair relation.  A downward walk toward the occupancy relation
    was considered and rejected: it reaches that relation through
    consumers S2 classifies as layer-blind, so it returns UNINDEXED for
    every state relation and separates nothing.  The resulting IN-VIEW
    label is EXISTENTIAL -- some consumer restricted to the view reads
    the relation -- and is printed with the count of view-blind read
    sites beside it, so it is never mistaken for exclusivity.  Nothing
    above is revised by this update and 7.27 stands as taken.
