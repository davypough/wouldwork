Crelay-Topo Backward Analysis -- Rules, Facts, Lemmas, Nogoods, Symmetries
==========================================================================

Shared register for Backward-Tree.txt and Backward-Justification.txt.
Numbering is global and permanent within each category.

Categories
  R   rule: domain semantics, with source file
  F   fact: problem-specific static or initial fact, with verification status
      (verified: checked against current files or a REPL query;
       unverified: inferred or from a possibly stale source)
  T   lemma: derived result reused at more than one node (T, not L,
      because L is a location; renamed 2026-09-18)
  G   nogood: minimal constraint set shown to be unachievable, with origin node
  Y   symmetry: equivalence used to group cases, with its validity conditions

Heuristic
---------

H1  f(N) = depth(N) + h(N), where depth(N) is the number of actions fixed
    between N and the goal, and h(N) is a landmark lower bound on the
    actions needed from the initial state to reach a state satisfying N's
    open conditions.  h counts distinct required action events (K below)
    not already realized by N's fixed suffix, plus events N's own
    conditions add.  Used only to order expansion.

    H1 is revisable, and revision is not optional.  Whenever analysis at
    a node shows a landmark wrong, missing, or miscounted, and the
    correction would change any f difference between open nodes, H1 is
    amended here and every affected f recomputed before the next
    expansion.  A correction that shifts the whole frontier equally may
    be recorded without recomputing; one that moves open nodes relative
    to each other may not, since the ordering would then rest on a count
    already known to be wrong.  K11, K12 and K13 all entered this way,
    each closing part of the same hole: h counted what must be true in
    the plate room and not what it cost to get it there.  The
    engine's own admissible bound is a cross-check: with the problem
    staged, (report-topo-finite-resource-bound-analysis *start-state*
    *goal*) reports its finite-resource bound, split into manipulation,
    routing, barrier, and session costs.  For this problem it reports 0
    (measured 2026-09-17): the finite-domain model drops every location
    task when the problem installs a blower drive
    (TOPO-RELAXED-PROPAGATING-RELOCATOR-P is true of blower1), and the
    session cost is 0 because the goal has no recorder conjunct.  So the
    engine's bound gives no cross-check here, and H1 stands on its own.

    Admissibility.  h is meant as a lower bound and is built like one --
    every K is argued as actions that are required and counted nowhere
    else, and every reading is the cheapest available.  It is not
    verified as one.  Two mechanisms can break it.  First, overlap: the
    Ks count pickups and walks in several places and assert they are
    distinct, but one MOVE spans a multi-gate route (R2), so walks
    counted apart may be one action; K15 already relies on exactly that
    to let one crossing cover another, and H2 exists because one action
    can fill several landmark roles.  Second, scope: an increment derived
    on one branch and applied by a blanket pass may overcharge a branch
    that escapes its premise -- which happened, when the ferry
    restatement charged the tray branch as three carries.
    This costs ordering quality, not correctness: nothing is pruned on f,
    and every X, R and deletion in this analysis rests on logic (T4, T7,
    T13, contradiction, census) rather than on a bound.  A branch mis-
    ranked is examined later, never lost.  Admissibility would matter if
    these numbers were ever offered to the engine as a cutoff, which is
    what the open topo-lower-bound item is about.

H2  Role consolidation.  One action may satisfy several landmarks at once:
    CONNECT-CONNECTOR both pairs a relay and depresses the plate it rests
    on; a tray put on a plate depresses it while its riders unload; a box
    on a plate is both occupant and a step up.  h counts such an action
    once, so consolidating cases do not get cheaper f automatically --
    they are preferred at equal f, on the principle that an object used
    for several roles can stand for the separate objects those roles
    would otherwise need.  Feasibility must still be checked: a carried
    connector is dark while held (R13), so a relay connector moved onto a
    plate lights again only if its retained pairings still have the
    geometry for it.

H3  Heuristic audit, run at every expansion, before the children are
    ranked.  Every landmark this analysis has added -- K11, K12, K13,
    K14, K15 -- was the same mistake: h counted a condition that must
    HOLD and not the actions that establish it.  The audit looks for that
    mistake deliberately instead of waiting for it to surface.  Take each
    condition of the node being expanded, and each condition its new
    children add, and ask:

    A  Provenance.  Does it put an object somewhere it does not start?
       Then a pickup and a landing are needed.  Is each counted?  K9
       counts a pickup only when it precedes a plate placement; K4 and K5
       count only plate landings.               [found K11, K12]
    B  Delivery.  Does it require a support occupied by something the
       node's own suffix does not put there?  Count the cheapest reading,
       live or ghost.                           [found K13]
    C  Access.  Does it require an apparatus state -- a switch, a beam, a
       gate -- that some body must be in a particular place to establish?
       Check the reach and walking facts for where that place is, and ask
       whether the travel there, and back if the body is needed
       elsewhere, is counted.                   [found K14, corrected F10]
    D  Session.  Does it require a ghost or a recorder session?  Then ask
       where the ghost forks, how it reaches where the node needs it, and
       whether its route replays on its own (P1).  Ghost travel is
       counted nowhere by default.              [found K15]
    E  Interference.  Does establishing one condition destroy another the
       branch needs later -- a plate vacated, a beam broken, a gate
       closed behind?  This yields an ordering constraint or a
       refutation, not an increment.            [found T13, T14]
    F  Dominance.  Would the state before this node already satisfy a
       node higher in the tree, or stand one move from the goal?  Then
       the branch below is deletable.           [T7, T13]
    G  Over-specification.  Is every condition listed actually required
       by this state, or has a precondition of some other action been
       copied in?  A condition that belongs to an achiever belongs on
       that achiever.                           [found N13's gate6 error]

    What to do with a finding.  An increment that changes any f
    difference between open nodes is applied and the affected f
    recomputed at once (the policy in H1).  One that shifts the frontier
    uniformly is applied too, since it is cheap and keeps h honest, but
    it reorders nothing.  Increments may be revised later: K13 was
    adopted at +1 and revised to +2 within the hour, when K15 priced the
    ghost reading it had assumed cheap.  A finding of kind E, F or G
    changes the node rather than the heuristic.

    The audit is recorded in each justification entry on an Audit line,
    naming the checks that fired and the checks that were run and came
    back clean, so that a gap found later can be traced to the node that
    should have caught it.

H7  Forward exact solving, and how the analysis ends.  H6 forbids
    BORROWED knowledge -- a solution someone already has.  It says
    nothing against GENERATED knowledge: solving an intermediate landmark
    exactly, from *START-STATE*, with a search that knows no more than we
    do.  That is fully available on an unsolved problem, and it is the
    backbone of the method rather than a concession to it.  Had the three
    struck tie-breaks been settled by measurement instead of by citation,
    they would have been sound.

    What an exact landmark solution yields, in increasing value:
      a NUMBER    an admissible contribution to h (H4).
      a WITNESS   the landmark is no longer hypothesized but established
                  as achievable, with a concrete prefix that achieves it.
      a STATE     the plan's end state is reachable and legal by
                  construction -- the property a hand-built state lacks
                  -- and can be chained onward as the next milestone's
                  start.
      a SHAPE     what the landmark forces about the configuration.

    The caveat on SHAPE, and it is the one that bites.  A single
    min-length plan is ONE witness.  That it ends with the ghost on
    plate1 and connector1 at location2 says nothing about how OTHER
    routes reach the same landmark, so no node may be refuted by
    disagreeing with a witness.  To conclude that EVERY route does
    something takes an exhaustion, not a plan.  Read a witness for what
    it proves possible, never for what it proves necessary.

    How the analysis ends.  The backward tree grows from the goal,
    establishing what must hold near it; the forward milestone chain
    grows from the start, establishing what is reachable.  They approach
    each other, and the method TERMINATES when they meet: a backward node
    whose complete condition set is satisfied by a reachable state gives
    a whole plan at once -- the chain's prefix, then the node's fixed
    suffix -- and that node is marked D.  Nothing in this needs a known
    solution, which is the point: the tree says where to aim the forward
    search, and the forward search says which parts of the tree are real.
    So a landmark the analysis has shown must be precisely achieved is
    exactly the right thing to spend a run on, and the run's end state is
    where the next run starts.

H6  Solution independence.  This method is being built for problems
    where no solution is known, so nothing in it may depend on one.  In
    particular no node's condition set, no exclusion, no landmark value
    and NO EXPANSION ORDER OR TIE-BREAK may cite a known solution.  A
    reason that could not be given on an unsolved problem is not a
    reason.
    This was violated three times early on, at 1.1, 1.1.1.1 and
    1.1.1.1.1.1, where the order cited "the validated solution's" choice.
    Those citations are struck; the entries now record what the choice
    rests on without it.  Two survive on independent grounds, and the
    third was later OVERTURNED by the retroactive f pass -- which is the
    argument in miniature: the borrowed reason was not merely unearned,
    it was wrong.
    The known solution may be consulted ONCE, after a branch has been
    carried to a checkpoint on its own, as a post-hoc check that the
    method found a solution at all.  It may not be consulted to choose,
    to rank, to prune, or to reassure.  Treat the subgoal-solution files
    as sealed during expansion.
    Note also that a sanity check is itself a dependency risk: a tree
    checked against a known answer as it grows will be steered by it
    unconsciously.  On an unsolved problem the confidence has to come
    from somewhere else, which is what H3's audit and H4's measurements
    are for -- both are solution-free, and both have overturned argued
    results here.  The one calibration that looked like it needed the
    94-action figure does not: that h is weak follows from a measured
    conjunct of 18 against a composed h of 19, and that comparison is
    available on any problem.
    H3 gains a check, run with the others:
      H  Provenance of the reasoning.  Could every reason given at this
         node have been given without knowing a solution?  If not, strike
         it and either find an independent reason or mark the choice
         arbitrary.

H5  Session hygiene.  This analysis lives in its files, not in a
    conversation.  When the context window of a working session grows
    long -- roughly when the running dialogue is larger than the three
    state files put together, or when earlier findings are being
    restated rather than remembered -- STOP EXPANDING, say so plainly,
    write the state files current, regenerate
    Backward-Continuation-Prompt.txt so that it alone carries the whole
    position, and recommend starting a fresh session from it.  Do not
    wait to be asked, and do not begin another expansion first: a step
    taken with a crowded window is the step most likely to repeat work
    already done or to contradict a lemma already recorded.
    The continuation prompt is the deliverable of that moment.  It must
    name the active path, the frontier by f, every landmark and lemma
    added since the last regeneration, the open questions with what is
    known about each, and the next step with its expected audit.

H4  Measurement.  The K values are argued, not measured, which is the
    admissibility weakness recorded in H1.  (SOLVE-SUBGOAL <start>
    <goal>) returns a guaranteed minimum-length solution when the depth
    cutoff is modest, under about 10, and that is exactly the size of a
    landmark cluster.  Two uses:

    Lower bounds by construction.  Drop everything but one landmark
    cluster and measure the minimum from *START-STATE*.  Relaxing a
    problem cannot lengthen its optimum, so the measured minimum is an
    admissible contribution to h for any conjunct every solution must
    satisfy.  A measured K needs no argument and cannot be argued wrong.

    Disjointness.  The overlap hazard is that two Ks count one action
    twice.  Measure A alone, B alone, then A and B together: if the joint
    minimum is less than the sum, they overlap, and the joint figure
    replaces the sum.  This tests directly what H1 can only assert.

    A search that exhausts its cutoff without a solution is also
    informative: it shows the conjunct costs more than the cutoff, which
    raises h, and where the conjunct is meant to be impossible -- the T15
    census, say -- exhaustion is a check on the counting argument.

    Limits.  The nodes of this tree sit near the goal, far beyond a
    modest cutoff from the start, so whole nodes cannot be measured; only
    clusters, and links between adjacent nodes.  A node's conditions are
    partial, so variables must be ground and the minimum taken over
    groundings.
    The practical ceiling, measured 2026-09-17: cutoff 14 on (open gate8)
    returned quickly; cutoff 17 took 395 seconds with *threads* 16 and
    still exhausted.  So for this problem the usable band is roughly 14
    and below, and anything needing 18 or more is out of reach by search.
    A REPLAYED state is different: VALIDATE-ACTION-SEQUENCE on a literal
    action list yields a legal reachable state that the two-argument
    SOLVE-SUBGOAL or any query can take (tests 7, 10, 11 did this), and
    its FAILURE-REASON names the first illegal action.  Actions must be
    written in the printed phrase form, e.g. (PICKUP-TRAY > AGENT1 picks
    up TRAY1 at LOCATION7 from LOCATION7); only MOVE and the recorder
    actions have short forms.
    Never hand-build a start state to get around that.  Test 4 did, and
    its null result could not be told apart from an illegal fact list --
    HOLDING prints as HOLDING1 and HOLDING2 and is not directly
    assertable.  A goal from *START-STATE* leaves only the goal to get
    wrong; a hand-built state tests the author as much as the model.

    Calibration, and it is sobering.  (open gate8) alone measures at 18
    or more, while the composed base h for the WHOLE problem is 19.  One
    conjunct of the goal nearly saturates the estimate of the whole --
    which is solution-free evidence, available on any problem, that h is
    admissible but very weak: the great bulk of
    every plan is invisible to the landmark count.  Since nothing is
    pruned on f this costs ordering only, but it means f differences of
    one or two near the frontier are close to noise, and the H3 audit --
    which finds structure -- has been worth more than the arithmetic.

Pruning analogues (from wouldwork's own search)
-----------------------------------------------

P1  Ghost-recording playability (the *RECORDER-PREFIX-PRUNING* analogue).
    A ghost action sequence must replay from the START-RECORDER snapshot
    in isolation; once an action in it fails, no later action repairs it.
    Backward analogue: a node whose conditions require ghost actions is
    checked for an isolated replay of those actions in recording-side
    state before being expanded, and marked X (with a nogood) if none
    exists.  Because a ghost replays independently of the live
    environment, this check is self-contained: no live state can rescue a
    ghost route that fails in the recording view, or break one that
    succeeds there.  A ghost branch's gate conditions are therefore
    recording-side conditions throughout.
    [-recorder-solution validate-recorder-recording-prefix]

P2  Cycle dominance.  At an equal boundary, a path using fewer recorder
    cycles dominates one using more.  Weakened 2026-09-17: cycling is the
    only way to move a ghost agent (K15, K16), and the measured optimum
    of test 2 spends a cycle to do it, so this orders equals and never
    argues against a cycle that buys something.  Backward analogue: between two
    branches whose conditions coincide, keep the one demanding fewer
    cycles; this is also why ghost cases carry an h increment.
    [-recorder-solution prune-recorder-boundary-dominated-successor-p]

P3  Interleaving canonicalization.  The search fixes one canonical
    interleaving of live and ghost actions.  Backward analogue: the
    unordered-condition convention -- do not branch on orderings of
    independent actions.

P4  Novelty and symmetry pruning.  Their backward analogues are already in
    use as T7 (no early satisfaction) and the Y symmetries.

Rules
-----

R1  An agent's has-location is written only by:
      (a) APPLY-AGENT-CONFIGURATION! in MOVE, for the moving agent;
      (b) RELOCATE-STACK! on a stack containing the agent, triggered by the
          holder of a held tray moving (APPLY-AGENT-CONFIGURATION!), by
          PLACE-HELD-OBJECT! for a tray (PUT-TRAY), or by floor-blower
          launch/drop.
    Recorder actions write has-location only for ghosts.
    [-configuration-transition, -support-motion, -placement, -floor-blowing,
     -recorder-session]

R2  A MOVE from the ground applies a route of traversal segments, each
    backed by a traverse-via or traverse-via> edge; a MOVE from a support
    applies exactly one configuration transition.  The final segment of a
    route ending at location L uses an edge into L.  A route may mix
    segment kinds: test 13 measured one MOVE as ((JUMP LOCATION20 NIL
    LOCATION5) (WALK LOCATION5 (GATE1) LOCATION2)).
    [-mobility-action, -mobility]

R3  A configuration transition either keeps the location (local mount,
    dismount, transfer) or lands remotely along an authored jumping edge.
    [jump.lisp, step.lisp]

R4  A walking segment requires equal endpoint levels, a safe destination,
    and every clause obstacle clear: a gate open (live agent) or
    recording-open (ghost); a screen or ladder only with empty hands.
    [walkability.lisp, -passability, -gate]

R5  Support use: fixed supports (plates) are shared by both layers; a mobile
    support must be on the occupant's recording side, except that a live
    occupant may use a ghost tray held by a ghost while recording is in
    progress (rule 19).  An agent cannot ride a tray it holds; a grounded
    tray is inert.
    [-recorder-core support-use-allowed, jump.lisp, -placement]

R6  An agent may manipulate (hold, place) only objects on its own recording
    side.  [-recorder-core object-manipulation-allowed]

R7  PUT-TRAY's target location must be reachable from the holder: the same
    location, or a reach-via / reach-via> edge whose gates are open.
    [tray.lisp, reachability.lisp]

R8  A floor blower relocates stacks only between its own position and its
    aimed-at destination.  [-floor-blowing]

R9  Search stops at the first state satisfying the goal, so the goal is
    false in every earlier state.

R10 Recorder actions.  START-RECORDER needs the live agent at the recorder
    and empty-handed; its fork adds each ghost at its live original's
    location, on the same fixed support if any, so it never newly occupies
    a plate.  CANCEL-PLAYBACK needs the live agent at the recorder.
    STOP-RECORDER (by the ghost) needs a boundary with no live object
    depending on a ghost object, and closing removes ghost state.  None
    writes a live object's has-location or on.
    [-recorder-session, -recorder-cycle-boundary]

R11 PUT-BOX, PUT-CONNECTOR, PUT-TRAY, and CONNECT-CONNECTOR place held
    cargo at a location reachable from the agent (same test as R7), on the
    ground or a clear support.  CONNECT-CONNECTOR also pairs the connector
    with selected connectable termini.  Placement changes neither the
    agent's location nor its support.
    [box.lisp, beam-relay.lisp, tray.lisp, -placement]

R15 Switch toggling and the two views.  TOGGLE-SWITCH needs the switch
    within reach (REACH-VIA) and within vertical reach; holding cargo does
    not prevent it.  A ghost actor flips both RECORDING-SWITCHED-ON and
    the live SWITCHED-ON, since a ghost's action is physical exactly as
    its weight is (plate.lisp).  A live actor flips only SWITCHED-ON, so a
    recorded ghost route keeps the gate states it was recorded under --
    which is what lets ordinary gate5 close while recording gate5 stays
    open.  Either agent can therefore undo the other's toggle.
    A ghost replays its recorded route and actions independently of the
    current environment: live changes never block it, and its own
    feasibility is decided entirely in the recording view (P1).
    [switch.lisp install-toggle-switch, amended 2026-09-17]

R13 Connector pickup and pairings.  Two lifts now exist
    (beam-relay.lisp, amended 2026-09-17):
      PICKUP-CONNECTOR                     clears every pairing, both
                                           directions
      PICKUP-CONNECTOR-RETAINING-PAIRINGS  keeps every pairing
    A held connector has no HAS-LOCATION either way, so RELAY-ANCHOR
    yields nothing for it and COMPUTE-RELAY-LIGHTING skips it: pairings
    can outlast a carry, a beam cannot.  Setting the connector down
    revives whatever its retained pairings can still light.  A connector
    riding a held tray, or a box on one, keeps its beam, because
    relocation keeps its HAS-LOCATION.                       [verified]

R12 A tray release relocates its riders with it.  A remote release unloads
    riders to the ground; a local release settles each rider on the highest
    clear support at or below its level (possibly the ground).
    [-placement place-held-object!, -support-settling]

R17 Placement reach.  An agent may set held cargo on a support whose top
    is at most *vertical-reach-limit* (1) above the agent's own base,
    and any distance below (WITHIN-AGENT-PLACEMENT-REACH in -support-
    elevation, used by PLACEMENT-OPTIONS).  A held tray's top is its
    holder's top, 3/2 for an agent on the ground, so live cargo goes
    onto a ghost-held tray only from a raised stand -- box1 (base 2) or
    another held tray -- or by settling from a tray release of equal
    height (R12).  Lifting is the symmetric WITHIN-AGENT-VERTICAL-REACH.
    Measured: test 13 W3, (on connector1 tray1*) exhausted at cutoff 3
    with agent1 two actions away on the ground.              [verified]

R16 The two views of gates and plates.  A live occupant or a ghost
    occupant depresses a plate for the LIVE view alike (UPDATE-PLATE-
    STATUS! uses SUPPORT-OCCUPIED, layer-blind), so a live gate opens
    under ghost weight.  The RECORDING view of a plate, while a cycle is
    open, counts GHOST occupants only (RECORDING-PLATE-OCCUPIED in
    -recorder-plate-shadow: a live occupant is read only after
    RECORDER-CYCLE-CLOSED, when no ghost exists).  A recording-side
    switch starts as a copy of the live switch at each fork (SEED-
    RECORDING-SWITCH-SHADOW!) and afterwards changes only under a
    ghost's toggle (R15).  RECORDING-OPEN is derived from those two by
    RECORDING-CONTROL-ON exactly as OPEN is from the live ones.  A ghost
    passes a gate only if it is RECORDING-OPEN (GATE-OPEN-FOR-OBJECT in
    -gate.lisp, reached by every walk through -passability); a live
    agent only if it is OPEN.  Consequences: a live gate can be held
    open for agent1 by a ghost, but a recording gate can be held open
    for the ghost only by a ghost object or by inheritance at the fork;
    a live toggle never opens a recording gate.
    [plate.lisp, -recorder-plate-shadow, -recorder-switch-shadow,
     -recorder-controls-shadow, -recorder-gate-shadow, -gate,
     -passability; all read 2026-09-18]                    [verified]
